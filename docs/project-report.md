# تقرير شامل — منصة الأتمتة والمبيعات متعددة القنوات (Matjar Bot)

تاريخ التقرير: بعد اكتمال 13 commit تغطي التصميم، قاعدة البيانات، الـ API، 13 n8n Workflow،
تطبيق أدمن جزئي، عقدة WhatsApp احتياطية، وتوسعة Instagram/TikTok.

## 1. نظرة عامة: ماذا يوجد فعلياً الآن

هذا المشروع **تصميم وتوصيل (wiring) كامل**، وليس نظاماً جاهزاً للتشغيل فوراً. الفرق مهم:
كل قرار معماري، كل جدول بيانات، وكل تدفق بيانات موثّق ومترابط بدقة — لكن **قطعتين
جوهريتين لم تُبنَيا كشيفرة فعلية بعد**: الـ Backend API نفسه (موجود كعقد/مواصفة OpenAPI
فقط)، وخدمة الـ AI (موجودة كعقد افتراضي داخل ملاحظات Workflow 02 فقط). كل الـ n8n
Workflows وتطبيق الأدمن **يفترضان** أن هاتين الخدمتين موجودتان وتتحدثان بالضبط بالشكل
الموثّق في `api/openapi.yaml`.

| الطبقة | الحالة | الملاحظة |
|---|---|---|
| Architecture + DB Schema | ✅ كامل | `docs/architecture.md`, `database/migrations/001_init_schema.sql` |
| OpenAPI (عقد الـ API) | ✅ كامل (32+ نقطة) | `api/openapi.yaml` — **عقد فقط، لا شيفرة خادم فعلية** |
| Backend API (شيفرة فعلية) | ❌ غير مبني | أكبر عمل يدوي متبقٍ — راجع القسم 3 |

## 2. الأمان والحماية — الأهم، وفيه فجوات حقيقية يجب سدّها قبل أي إطلاق فعلي

هذا القسم يستحق أكبر قدر من الانتباه لأنه **الجزء الذي لم يُبنَ فعلياً بعد** (كل شيء هنا
عقد/تصميم)، وبعض القرارات الأمنية الحرجة لم تُتَّخذ بعد ضمن ما بنيناه.

### 2.1 فجوات حقيقية موجودة الآن في التصميم — يجب سدّها قبل الإطلاق

- **لا يوجد تحقق من توقيع Webhooks (Signature Verification)**. Workflows 01 و09
  تتحقق من `hub.verify_token` عند **ربط** الـ Webhook لأول مرة فقط — لكن **كل رسالة لاحقة**
  تصل بلا أي تحقق من أنها فعلاً من Meta. Meta ترسل header اسمه `X-Hub-Signature-256`
  (HMAC-SHA256 موقّع بـ App Secret) مع كل حدث — يجب إضافة عقدة تحقق من هذا التوقيع في
  بداية كل Workflow webhook (01, 09) قبل معالجة أي محتوى، وإلا يستطيع أي شخص يعرف رابط
  الـ Webhook إرسال رسائل مزيَّفة للنظام.
- **لا يوجد انتهاء صلاحية (expiry) أو تجديد (refresh) لتوكن الأدمن**. `POST /auth/login`
  يُصدر JWT واحداً يبقى صالحاً إلى الأبد عملياً (يُخزَّن في `expo-secure-store` ويُستخدم
  للأبد). لو سُرق الهاتف مفتوحاً، لا توجد طريقة لإبطال ذلك التوكن عن بُعد. يحتاج: توكن
  قصير الأجل (ساعة مثلاً) + refresh token، أو آلية Revocation List على الأقل.
- **لا توجد نقطة نهاية لإنشاء أول حساب أدمن**. صممت `POST /auth/login` لكن لا يوجد
  `POST /auth/register` أو ما يعادله — إنشاء أول حساب أدمن يحتاج script/seed يدوي مباشر
  على قاعدة البيانات عند التشغيل الأول (وثّق هذا بوضوح في أي دليل نشر تكتبه لاحقاً).
- **لا يوجد Rate Limiting موثّق على أي نقطة نهاية** — تحديداً `/auth/login` (عرضة لهجوم
  تخمين كلمة مرور) و`/orders` (عرضة لإنشاء طلبات وهمية بالجملة إذا سُرّب التوكن الداخلي
  المستخدم بين n8n والـ Backend).
- **صلاحيات الأدمن كلها متساوية** — أي حساب أدمن مسجَّل دخوله يستطيع قبول/رفض أي طلب،
  والرد نيابة عن أي محادثة، والنشر على الصفحة. لا فصل أدوار (مثلاً: موظف يرى الطلبات فقط
  دون صلاحية النشر).

### 2.2 قرارات أمنية اتُّخذت بالفعل (نقاط قوة، وليست فجوات)

- **كل توكن حساس (WhatsApp, Facebook, S3, Evolution, خدمة Push) يبقى مركزياً في
  الـ Backend فقط** — n8n لا يحمل أياً منها مباشرة إلا `WHATSAPP_ACCESS_TOKEN` نفسه
  (ضروري لأن n8n يرسل الرسائل مباشرة)، وحتى ذلك محصور في Workflow واحد مشترك
  (`00 - Send WhatsApp Message`) بدل توزيعه على كل Workflow.
- **رفع الملفات (إثبات التحويل، وسائط المنشورات) عبر presigned URLs** — بيانات اعتماد
  التخزين (S3) لا تُشارَك مع n8n أو التطبيق إطلاقاً.
- **توكن الأدمن يُخزَّن عبر `expo-secure-store`** (خزنة نظام التشغيل الآمنة) وليس تخزيناً
  عادياً — قرار صحيح، لكنه غير كافٍ وحده بدون معالجة فجوة انتهاء الصلاحية أعلاه.
- **عمليات حساسة محمية بـ Idempotency-Key** (إنشاء طلب، قرار الأدمن، ربط إثبات تحويل،
  الرد على تعليق) — يمنع التكرار الناتج عن إعادة محاولة الشبكة.

### 2.3 أشياء يجب فعلها عند بناء الـ Backend الفعلي (لم تُذكر أعلاه)

- تشفير عمود `access_token_ref` وأي بيانات حساسة أخرى في قاعدة البيانات (Encryption at
  Rest)، وليس فقط "الإشارة إليه" كما ورد في التصميم.
- Input validation صارم على كل نقطة نهاية (خصوصاً أرقام الهواتف والعناوين القادمة من
  رسائل WhatsApp الحرة — لا تثق بأي نص وارد من العميل أو حتى من AI بلا تحقق).
- Parameterized queries حصراً (منع SQL Injection) — بديهي لكن يستحق الذكر صراحة كمعيار
  قبول (acceptance criterion) عند مراجعة كود الـ Backend.
- سياسة الاحتفاظ بالبيانات وحذفها (Data Retention): صور إثبات التحويل تحديداً قد تحتوي
  تفاصيل حساب بنكي — حدّد مدة احتفاظ واضحة وآلية حذف دورية.
- CORS مضبوط بدقة على الـ Backend (لا `*`) — الأصول المسموحة فقط: تطبيق الأدمن وn8n.
- تحديث Evolution API بانتظام (إن استُخدمت) — كونها تحاكي بروتوكولاً غير رسمي، ثغرات
  الأمان فيها قد تُكتشف وتُصلَح بوتيرة مختلفة عن Meta الرسمية.

## 3. أهم عمل يدوي متبقٍ (بترتيب الأولوية الفعلي)

1. **بناء الـ Backend API فعلياً** يطبّق `api/openapi.yaml` حرفياً — هذا يُشغِّل كل شيء
   آخر. بدونه، كل Workflow وكل شاشة في التطبيق مجرد واجهة بلا وظيفة.
2. **بناء خدمة الـ AI** (`/nlu` و`/compose-reply`) — أبسط مسار عملي: نداء إلى Claude أو
   نموذج مشابه بموجّه (prompt) يُلزمه بإخراج JSON منظّم لكل من الفهم والصياغة، مع تمرير
   `grounding_data` الحقيقي كما هو موثّق في ملاحظات Workflow 02 — **بدون** السماح للنموذج
   باختلاق أرقام لم تُرسَل إليه.
3. **إنشاء أول حساب أدمن** يدوياً (راجع الفجوة 2.1) بعد بناء الـ Backend.
4. **حسابات المنصات الفعلية**: Meta Business verification لـ WhatsApp Cloud API +
   Facebook App review لصلاحيات الصفحة/Instagram + (اختياري) نشر Evolution API + (اختياري)
   تسجيل تطبيق TikTok.
5. **نشر n8n** (سحابياً أو ذاتياً)، استيراد كل ملفات `n8n-workflows/` بالترتيب من 00،
   وربط كل عقدة Execute Workflow يدوياً بعد الاستيراد (القيمة `workflowId.value` فارغة
   عمداً — n8n يملأها من القائمة المنسدلة بعد الاستيراد).
6. **بناء أول APK فعلي** (خطوة تفاعلية واحدة عبر `eas build` محلياً، موثّقة في
   `admin-app/README.md`) قبل الاعتماد على GitHub Actions التلقائي.
7. **تعبئة بيانات المنتجات الأولية** في قاعدة البيانات (لا يوجد أي منتج افتراضي).
8. **سد فجوات الأمان في القسم 2.1** — تحديداً توقيع الـ Webhooks وانتهاء صلاحية التوكن،
   قبل أي استخدام بأموال/عملاء حقيقيين.

## 4. توصيات للتحسين والتوسيع (اختيارية، مرتبة حسب القيمة المتوقعة)

- **لوحة تحليلات بسيطة**: مسار تحويل واضح (تعليق فيسبوك ← Messenger ← WhatsApp ← طلب
  مكتمل) يكشف أين يتسرّب العملاء المحتملون فعلياً — البيانات كلها موجودة أصلاً في
  الجداول، تحتاج فقط استعلامات تجميعية وشاشة عرض.
- **تذكير تلقائي للطلبات المتروكة**: عميل بدأ طلباً (`WAITING_FOR_CUSTOMER_DATA` أو
  `WAITING_FOR_PAYMENT`) ولم يكمله خلال ساعات — رسالة WhatsApp لطيفة تذكّره، عبر Workflow
  cron جديد شبيه بـ `08 - Scheduled Posts`.
- **تنبيه نفاد المخزون قبل حدوثه**: إشعار للأدمن عند وصول `quantity_available` لعتبة
  منخفضة، بدل اكتشافه فقط عند اختيار الأدمن "نفذت الكمية" لطلب فعلي.
- **صفحة تتبّع طلب للعميل** (رابط بسيط يُرسَل ضمن رسالة رقم التتبع) — تقليل استفسارات
  "وين طلبي" المتكررة عبر WhatsApp.
- **صلاحيات أدوار متعددة للأدمن** (راجع الفجوة 2.1) — أولوية إن كان الفريق أكبر من شخص
  واحد أو اثنين.
- **تحسين تدريجي لجودة AI**: تسجيل كل تصعيد بشري (escalation) مع سببه يبني أرشيفاً فعلياً
  لتحسين موجّهات NLU بمرور الوقت — الجدول (`conversations.status = escalated_to_human`)
  موجود أصلاً، يحتاج فقط تقريراً دورياً يراجعه أحد.
- **دعم أكثر من لغة** إن توسّع النشاط التجاري خارج نطاق عربي بحت — يمس بنية `/nlu` و
  `/compose-reply` بإضافة معامل `language` (Workflow 03 يمرره جزئياً في مسار الدفع فقط
  حالياً).

## 5. ملخص تنفيذي من سطرين

النظام **مُصمَّم ومُوصَّل بالكامل** من أول رسالة WhatsApp وحتى استلام الأدمن للطلب، ومن
تعليق فيسبوك/إنستغرام وحتى وصول العميل لـ WhatsApp — بما في ذلك عقدة احتياطية إن تعطّل
API الرسمي. **الفجوة الوحيدة الحقيقية بين هذا وبين نظام يعمل فعلياً هي بناء خدمتين
(Backend + AI) تطبّقان العقد الموثّقة بدقة**، بالإضافة لسدّ فجوتي الأمان الحرجتين (توقيع
الـ Webhooks، وانتهاء صلاحية التوكن) قبل أي استخدام حقيقي بأموال العملاء.
